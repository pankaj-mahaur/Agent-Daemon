# Memory in other agents: the installer

ad's memory server gives Claude Code, Codex, Cursor, VS Code and Gemini CLI the lessons and
corrections from your past sessions in the same project. One command adds it to
each host you have:

```sh
npx agent-daemon-memory install
```

With ad installed, `ad memory install` does the same, pointing the hosts at your
ad install instead of a copied package.

It shows the plan and asks first:

```
ad memory — install
Found: Claude Code, Cursor. Not found: Codex.
  Claude Code  add the memory server with `claude mcp add` (user scope). ad's hooks already capture here, so the record tools stay off.
  Cursor       add to ~/.cursor/mcp.json (backup first). No ad hooks here, so capture uses the record tools.
Memory stays on this computer: ~/.agent-daemon/episodic.db. No account.
Continue? [Y/n]
```

Then restart each host. Exit code: 0 all set up, 2 some hosts refused, 1 nothing done.

## The hosts

| Host | Where the entry goes | Capture | Project the server serves |
|---|---|---|---|
| Claude Code | `claude mcp add --scope user` (ad never edits `~/.claude.json`, which Claude Code rewrites itself) | ad's hooks when `ad init` set them up, else the record tools | the open project (`CLAUDE_PROJECT_DIR`) |
| Codex | `~/.codex/config.toml` (or `$CODEX_HOME`), one line under `[mcp_servers]` (`codex mcp add` leaves it as written) | the record tools | the session's folder |
| Cursor | `~/.cursor/mcp.json` | the record tools | `${workspaceFolder}`, else the working folder if it is a project |
| VS Code (Copilot) | `~/.copilot/mcp-config.json` (or `$COPILOT_HOME`), the personal file VS Code's docs prefer | the record tools | the open workspace folder (VS Code starts the server there) |
| Gemini CLI | `~/.gemini/settings.json` (or under `$GEMINI_CLI_HOME`); ad edits the file itself, its own entry only (`gemini mcp add` defaults to the project scope) | the record tools | the folder Gemini runs in, if it is a project |

`--host <id>` (`claude-code`, `codex`, `cursor`, `vscode`, `gemini`) picks hosts; `--capture
auto|hooks|tools` overrides the capture mode; `--dry-run` shows the plan and the
snippets and writes nothing; `--yes` skips the question; `--no-plugin` sets up
Claude Code's memory hooks without the plugin (see Setup below).

Hosts start the server with the absolute path of the Node that ran the
installer (GUI apps often don't have your shell's PATH), through a stable
launcher: `~/.agent-daemon/memory/launch/run.mjs serve …`. The npx install keeps
a copy of the package with its two parsers in
`~/.agent-daemon/memory/dist/<version>/` (the two newest versions); `ad memory
install` registers your clone instead. Hosts never run `npx`, and an upgrade only
changes which copy the launcher starts: no entry changes, so no host asks you to
trust anything again. It needs Node 22.16 or newer and builds nothing: memory
runs on Node's built-in SQLite. A hook whose package is gone exits quietly and
tells you once per session to run `npx -y agent-daemon-memory@<version>
uninstall`.

Upgrading from 3.1.0: install moves its entries (they started
`~/.agent-daemon/memory/bin/launch.mjs`) to the launcher, and Codex's from the
block between ad's markers to the one-line form (also when `codex mcp add` has
since moved the markers). 3.1.0's package copy (`memory/pkg/`, `memory/bin/`)
stays until uninstall.

Gemini CLI disconnects local servers in folders you haven't trusted: trust the project folder in Gemini if the memory tools are missing.

With ad's memory plugin enabled in Claude Code, install leaves Claude Code alone (one route per host). Plugins (Claude Code's marketplace, Agent Plugins for VS Code and others) are the other way in: [Memory as host plugins](hosts.md).

## Setup: the hooks (Claude Code, Codex)

```sh
npx agent-daemon-memory setup               # in your own terminal: every host found
npx agent-daemon-memory setup --no-plugin   # Claude Code without the plugin
npx agent-daemon-memory setup --host codex  # one host
```

`setup` adds what a plugin can't add to Claude Code's user `settings.json`
(`$CLAUDE_CONFIG_DIR/settings.json` when that is set), each through the stable
launcher:

- **With the plugin on:** the `PreToolUse` entry that checks tool calls before
  they run (`tool.before`; with no rules yet it does nothing), written so it can
  never block a tool call if it fails (`onFailure: "continue"`), and
  `env.AD_TOOL_SHELL = "1"`, which marks the agent's own shell so it can't accept
  notes or change ad's settings for you.
- **With `--no-plugin`:** every memory hook the plugin would bring (session
  start, prompt capture, the scheduled-prompt and subagent records) plus the two
  above.
- **Neither:** nothing is written; setup prints the two `/plugin` lines.

From a clone of ad, the same command is `ad memory setup`. With `ad init`'s
own hooks in place and no plugin, setup writes only the marker.

A hook that `ad init`'s own hooks already run is skipped, so nothing runs twice.
Claude Code older than 2.1.314 gets no hooks (it may ignore the form ad writes);
update it and run setup again. An `AD_TOOL_SHELL` you set to something else is
left as it is. Setup only adds lines (it never re-lays out yours), checks the
result parses to exactly what it meant, and writes only over the bytes it read:
if Claude Code writes the file meanwhile, setup plans again once, then stops and
asks you to re-run it. Before its first change it keeps a copy of the file under
`~/.agent-daemon/memory/backups/claude-code/`, and it asks before writing
through a linked settings file. Running it again changes nothing; an uninstall
right after gives the file back byte for byte (and removes a settings file setup
created).

**Codex.** Setup adds the memory hooks (session start, prompt capture, and the
check before Bash, Write and Edit calls) to `~/.codex/hooks.json` (or
`$CODEX_HOME`), or to `config.toml` when that file already holds hook lists, and
`AD_TOOL_SHELL = "1"` under `[shell_environment_policy.set]` in `config.toml`.
Each hook is the same single line, `node "<~/.agent-daemon>/memory/launch/run.mjs"
hook <event> --host codex`, so updates never change it. Codex runs a new hook
only after you trust it: open Codex and run `/hooks`. Setup adds its hooks after
yours, so the hooks you already trusted stay trusted. On Windows the check before
tool calls waits for your first rule (Codex starts a shell for every hook, which
costs a second or more per tool call). An ad folder whose path holds `$`, a
backtick, `%` or `"` gets no Codex hooks (Codex's shell would read them); set
`AD_ROOT` to a plain path. If `include_only` in your `shell_environment_policy`
would drop `AD_TOOL_SHELL`, setup says so. When the marker later disappears from
`config.toml`, the next Codex session says how to put it back. Uninstall removes
Codex's entries only as setup wrote them and never edits one you changed (Codex
would stop trusting it); it says when hooks you added after ad's need trusting
again in `/hooks`.

`install` runs setup at the end when it has something to do. Setup needs a
terminal: run without one (a script, an agent's tool), `install` adds the MCP
entries, then prints `Finish in a terminal: npx -y agent-daemon-memory@<version>
setup` and exits 2. `install --no-setup` adds only the MCP entries, with their
own exit code (for scripts and CI). In Git Bash (mintty) node sees no terminal: use `winpty`,
PowerShell or Windows Terminal. `install`, `setup`, `repair` and `uninstall` all
refuse to run from the agent's own shell.

## What it never does

- Change anything in a host's config but its own entry. JSON keeps your
  comments, order and formatting; TOML gets one line under `[mcp_servers]`.
- Edit a file it can't edit safely. It refuses, leaves the file as it is, and
  prints the snippet to add yourself, when: the file doesn't parse; Codex's
  `mcp_servers` isn't a table; `agent-daemon-memory` is already there and
  isn't ad's (in any TOML shape: a table, dotted keys, an inline table), or is
  ad's but you edited it; the file is read-only or isn't UTF-8 text; the file
  changed while it was asking you; or the config is ad's own engine home (also
  through a link).
- Write through a linked config (dotfile managers) without asking you, even
  with `--yes`.
- Touch your memory data on uninstall, unless you ask (`--purge-data`, typed).

Before the first change to a file it keeps the original under
`~/.agent-daemon/memory/backups/<host>/`, and records what it did in
`~/.agent-daemon/memory/install-ledger.json`.

## Doctor, repair, status, uninstall

```sh
npx agent-daemon-memory doctor        # --json for the check codes
npx agent-daemon-memory repair        # put back the entries it owns
npx agent-daemon-memory status
npx agent-daemon-memory uninstall     # --host <id> for one host
```

`doctor` starts each installed entry the way the host does and talks to it with
both MCP handshakes. Its codes: `node.version`, `node.path`, `sqlite.driver`,
`db.open`, `db.schema`, `db.stray`, and per host `config.parse`, `entry`,
`command.exists`, `smoke.legacy`, `smoke.modern`, `capture.double`, `route.double` (Claude Code: the installer's entry and the plugin both serve memory),
`entry.duplicate`; `pkg.stale` when an older version is installed; `hooks.trust`
(Codex: whether you trusted setup's hooks in `/hooks`: trusted, not reviewed yet,
changed since you trusted them, or turned off).

`uninstall` puts a file back exactly as it was when nothing else ever changed
it between ad's writes (or removes it, if ad created it). If anyone else wrote
to the file since the first install, it removes only ad's entry and keeps
everything else; an entry you edited yourself stays, with a message. Claude
Code's entry goes through `claude mcp remove --scope user`; a same-named entry
you added in another scope is never touched. Removing the last host also
removes the launcher, so an entry you copied by hand into another program stops
working.

Setup's hooks and marker go one by one, found by what they are rather than
where they sit: only an entry that still starts ad's launcher and that you
haven't changed is removed, and `env.AD_TOOL_SHELL` stays if you had it before
setup. A hook entry you changed stays, with `onFailure: "continue"` so it can't
block a tool call, and the host is marked uninstalled, so the entry does
nothing; if you later delete `~/.agent-daemon`, Claude Code shows node's
missing-file error for it and carries on. The launcher
(`~/.agent-daemon/memory/launch/`) and its copies go only when no config still
starts it. Once you have rules (a later release), removing the `tool.before`
entry or the marker needs your review in your own terminal; without it,
uninstall removes everything else and prints the exact manual step for each of
those two.

It ends with a summary in three lists: **Removed** (each entry ad took out),
**Kept** (each entry left in place, and why: you edited it, or you had it
before, with how to remove it) and **Left on disk** (your memory notes, the
per-project journals, the backups of your config files, the hook log, and the
launcher while something still starts it), so nothing stays behind without your
knowing.
`~/.agent-daemon/memory/ledger.json` records one line per item ad wrote into a
host's settings; the older `install-ledger.json` stays as it is, for earlier
versions of the package.

An `npx agent-daemon-memory install` of a newer version updates the copy the
launcher starts, even when every host is already set up. `--purge-data` also deletes the memory database after you
type `delete my memory`; it refuses while ad itself uses the same memory,
unless you add `--force`.

## Reviewing what agents record

In hosts without ad's hooks, the agent saves corrections with the record tools,
for your review. Accept them in your own terminal:

```sh
npx agent-daemon-memory review     # or: ad review
```

See [the memory server](../../mcp/agent-daemon-memory/README.md#recording-lessons-on-hosts-without-hooks).

## Windows notes

- `claude` starts by full path, without a shell: a native `claude.exe`, or the
  script behind npm's `claude.cmd`.
- A config another program has open is retried for a moment, then left
  unchanged with a message.
- Paths with `'` are written as escaped TOML strings.

If something goes wrong: [troubleshooting](../troubleshooting.md#53-the-memory-installer-refused-my-config).
